# Systemika Studio build-toolchain security note

## Scope

Systemika Studio's application payload has no production npm dependency tree. npm is used for the Electron development runtime and for release packaging tools; those packages are not copied into Systemika as application-level libraries.

## 1.0.0 release hardening

Before the first public release, the packaging layer was simplified to reduce unnecessary dependency exposure:

- Upgraded Electron Builder from `26.0.0` to `26.16.1`.
- Removed Gulp, `gulp-useref`, and `gulp-rename` from the release packaging project.
- Replaced the Gulp staging pipeline with `distribute/build.js`, which uses only Node.js built-in modules.
- Removed the obsolete inherited `OpenSystemDynamics/distribute/` Gulp 3 packaging helper.
- Pinned the packaged Electron runtime to `44.3.0` in the builder configuration.
- Disabled electron-builder's native npm rebuild phase because Systemika has no native npm modules.
- Pinned Electron Builder's AppImage toolset to `1.0.3`, which uses the modern static runtime and avoids a runtime dependency on legacy FUSE2 (`libfuse.so.2`).
- Moved ordinary build commands to `npm install --no-audit --no-fund`; maintainers can run the explicit `npm run audit:build` command when reviewing the build toolchain.

The upgrade removes the old electron-builder 26.0.x path that pulled `@electron/rebuild` 3.x and vulnerable/deprecated `tar` 6.x tooling. The AppImage toolset pin also avoids Electron Builder v26's legacy FUSE2-based AppImage default. Electron Builder 26.16.1 belongs to the maintained v26 line. Its own transitive tool dependencies may still emit deprecation notices, notably from legacy ASAR/glob tooling; those notices concern the installer build environment rather than the Systemika runtime payload.

## Dependency resolution

The release archive does not vendor `node_modules`. The direct packaging dependency is pinned exactly (`electron-builder` 26.16.1), and the Electron runtime is pinned exactly (44.3.0). npm will create/update `distribute/package-lock.json` when packaging dependencies are installed on a connected build machine; keeping that generated lockfile with an institutional release build is recommended when byte-for-byte dependency resolution needs to be reproduced later.

Do not substitute a hand-written or copied lockfile from an unrelated project: a trustworthy lockfile must be generated by npm from this package manifest and registry metadata.

## Release rule

Do not run `npm audit fix --force` on a release candidate as an automatic remedy. Forced major/transitive changes can alter the packager in untested ways. Instead, update the pinned build tool deliberately, rebuild the installers, and run the full Systemika regression suite.
